# 某主流记账 App（v6.7）架构静态分析（匿名版）

> 分析对象：一款国内主流个人记账 Android 应用，版本 6.7.x，2025 年发布。
> 方法：APK 静态分析（`aapt2` 清单/资源 + `baksmali` 字节码），未运行目标程序、未抓包、未做动态调试。
> 说明：按合规要求隐去应用名、包名、域名、证书指纹与自有接口路径；结论只描述架构与工程取舍。

## 1. 体量概览

| 维度 | 观测值 |
|---|---|
| dex 数量 | 4 个（`classes.dex` ~ `classes4.dex`） |
| 自有类（业务包内） | 约 8360 个 |
| 页面 | Activity 约 3400 个、`Fragment` 约 350 个、`dialog` 约 1100 个、`adapter` 约 950 个 |
| 数据实体 | 90 个 ORM 实体（schema version 2761） |
| 网络接口 | 单个 Retrofit Service 中约 192 个方法（129 POST + 76 GET） |
| 权限 | 27 项 |
| 桌面组件 | 10 个 Widget + 若干快捷磁贴 |

结论：这是一个功能完整度极高、迁移历史极长的个人财务客户端，复杂度主要来自资产/负债/投资体系，而非"记账"本身。

## 2. 技术栈画像

- **语言/构建**：Java + Kotlin 混合，Gradle/AGP 构建；大量 ButterKnife 注解绑定（说明代码年龄偏大）。
- **UI**：`AppCompatActivity` + Material Components；自定义浮球/Voice 交互控件。
- **数据层**：LitePal ORM，数据库落内部存储，**未使用 SQLCipher**（全包无 sqlcipher 引用）。
- **网络**：Retrofit2 + OkHttp；多媒体播放用 ExoPlayer2；图片用 Glide 系。
- **混淆**：组件名、实体名、SDK 名基本可读，字符串未加密——静态可读性很高，与"刻意抬高逆向成本"的部分（见 §5）形成反差。

## 4. 语音记账链路（重点）

这是本次分析中最具对比价值的一条链路，因为它揭示了"云端 ASR + 本地语义解析"的分工方式。

### 4.1 分层

1. **录音层**：`AudioRecord` 采集 PCM（16kHz、单声道），自管理缓冲区与静音判定。
2. **会话申请**：先向自有服务端申请一次识别会话，服务端校验账号与会员身份后下发 `SpeechSession{ token, wsUrl, model, maxSeconds, expiresAt }`；非会员直接返回 `not_vip`。
3. **流式识别**：客户端用临时 `token` 直连**第三方云厂商的实时语音 WebSocket**（协议字段：`run-task` / `result-generated` / `finish-task` / `heartbeat`，模型名为 `paraformer-realtime-v2` 一类，`format=pcm`、含 `max_sentence_silence`、`max_duration`、`language_hints`），边录边出中间结果。
4. **超时上报**：识别结束调用 `speechOvertime`，把本次消耗时长回报给服务端（用于额度计量）。
5. **本地语义解析**：识别出的**文本**交给自有 `recognize` 包（37 个类）做金额/分类/时间抽取，产出 `BillInfo`，再走本地入库。

### 4.2 三个关键判断

- **ASR 在云端，语义解析在本地**：文本解析器做了非常细的中文规则（分类词典、同义表达、金额与时间表达），这部分是纯本地、可离线、可单测的逻辑。
- **能力按会员分级**：识别会话需登录态 + 会员额度，非会员被服务端拦下（`not_vip`）。即"语音记账"是付费能力。
- **音频离开设备**：PCM 直接送给第三方云厂商，虽然走加密 WebSocket，但语音内容与账号绑定；对"财务对话"这类敏感文本，这属于需要明确告知的数据流向。

## 5. 工程亮点

1. **API 路由下沉 Native**：Retrofit 注解里的 path 全是占位符（形如 `__g44553__`），运行时由拦截器取出数字、调用 native 方法从 `.so` 里取真实路径/host/密钥。静态看 dex 无法还原完整接口清单。
2. **反篡改**：native 层扫描 `/proc/self/maps`、进程名、包路径，检测常见"签名杀手"与 Hook 框架特征；服务端另用 APK 签名摘要二次校验，防二次打包。
3. **无障碍自动记账的工程化**：监听 28 个应用，内部自定义广播协议驱动通知栏常驻状态（运行中/已暂停），按规则生成"待确认账单"再让用户确认——流程设计克制（不静默写入）。
4. **本地 MCP 服务**（该版本新增）：基于内嵌 HTTP 服务实现 MCP（JSON-RPC 2.0），随机令牌 + 常量时间比较 + Origin/Host 双向校验 + 写操作显式开关 + 空闲超时，安全基线明显高于同类"本地服务"实现。

## 6. 工程短板（对我们最有借鉴价值的部分）

| 问题 | 观测 | 影响 |
|---|---|---|
| 本地数据库明文 | ORM 落盘无加密 | Root/备份提取即全量账目泄露 |
| WebDAV 备份未加密 | 打包 zip 内含 `.db` 原文 | 账单进第三方网盘即外泄 |
| 允许明文流量 | `usesCleartextTraffic=true` | 放大了降级风险 |
| 密码无客户端哈希 | 登录/改密直接上送明文口令 | 依赖 TLS，抓包场景危险 |
| 无障碍权限面过大 | 28 个金融/电商 App 窗口内容可读，且服务类名套用其他应用的命名 | 权限被滥用即为高敏风险，用户认知不透明 |
| AI 图片外传 | 截图经对象存储上传云端识别 | 财务截图离开设备 |
| 签名方案停留在 v2 | 无密钥轮换 | 密钥泄露后只能换包名 |
| 反混淆不彻底 | 实体名/组件名/字符串全部可读 | 业务逻辑易被完整还原 |

**对个人财务类产品，最该优先补的是"本地数据 + 备份加密"**：其余短板都需要特定攻击面，而这一条在"手机送修/二手转卖/备份到网盘"这类日常场景下就会真实发生。

## 7. 复现方式（工具链）

```bash
# 清单与权限（无需反编译）
aapt2 dump badging target.apk
aapt2 dump xmltree --file AndroidManifest.xml target.apk

# 资源与清单（apktool 需可写 framework 目录）
java -jar apktool.jar d -f -s --frame-path /tmp/apktool-fw -o out target.apk

# 字节码（速度快、信息无损，本报告主要依据）
java -jar baksmali.jar d out/classes3.dex -o smali/c3
```

经验：3 万+ 类规模下 JADX 反编译耗时极长（>30 分钟未产出），改用 smali 定向检索更高效——先靠字符串常量定位可疑点（如 `paraformer`、`not_vip`、`run-task`），再沿调用链读方法体。

## 8. 结论

这款产品展示了"功能完备"与"数据安全"之间的典型失衡：功能侧做到了房贷/分期/报销/多币种投资全覆盖，工程侧却在最基础的本地数据加密上留白；同时把 API 路由与密钥下沉 native、叠加反篡改，说明团队对"防逆向"的重视程度高于"防泄露"。

对本次自己的项目（记一笔 Lite）而言，这份分析给出的三个决策依据是：

1. **复杂度要砍在数据模型层**：90 实体的维护成本会持续产生（schema version 2761 即迁移包袱），而不是只在开发期付一次。
2. **语音能力可以完全离线**：云端流式 ASR 换来的是更好的识别率，代价是登录、会员、音频出设备；对"老人 + 财务"这种隐私敏感场景，离线小模型 + 热词纠错的性价比更高。
3. **安全基线要一开始就立**："数据不出设备"是最省成本的安全设计——一旦引入云账号与同步，加密、备份、密钥管理全都得重新设计一遍。
